# R003 — Measure scheduling, memory and tile granularity

Status: planned. Suggested owner: **Astra**. Scope: one focused implementation session unless explicitly bounded as research; split with coordinator approval if unexpected work appears.

## Objective

Set concrete parallel scheduling thresholds and budgets from the single-worker baseline.

## Prerequisites

[T029](T029.md). These must meet their acceptance gates before dependent work starts.

## Files and modules

Create planned docs/research/R003-performance.md and controlled runner result manifests; experiments under experiments/scheduling/. All creation paths in this section are planned; inspect for intervening implementations before editing.

## Technical contract

Measure 5500U-class controlled hardware (or label substitute), workers1/2/4/8, tiles16/32/64/128, small-dialogue and heavy KFX; include CPU time/RSS/native context cost and scheduling overhead. Derive deterministic cost estimator from glyph/segment/pixel/filter work, not wall-clock history.

## Expected behavior

Some workloads may remain inline; report latency and total work so more threads cannot appear successful solely from speedup. Test memory reservation success independent of worker count and whether 16 face handles/worker is affordable.

## Implementation guidance

Maximum two focused experiment sessions once hardware is available. Publish uncertainty/variance and chosen thresholds; if hardware is unavailable, preserve portable benchmark infrastructure but do not invent thresholds or enable automatic workers.

Read [ARCHITECTURE](../ARCHITECTURE.md#a5-execution-and-determinism). Read [TESTING](../TESTING.md#v8-performance-and-kfx).

## Acceptance criteria

Architect chooses stage batching thresholds, tile size and conservative worker policy based on raw results; defines calibrated performance-regression review limits separately from correctness.

## Verification

At least30 samples/config plus independent repetitions, fixed build/power/thermal record, output equality for all experiment configurations. Publish raw data and analysis. Commands referring to Cargo/xtask are established by the task that creates that tooling; do not report them run before it exists.

## Forbidden changes

No regression tolerance changes, claimed 5500U results on another CPU, runtime schedule-dependent semantics or hosted-runner definitive speed claims. Ordinary implementation cannot modify protected expected assets, tolerances or support classifications.

## Completion report

Report R003, integration base and commit IDs (or explicitly no Git), changed files, exact commands and pass/fail results, fixture/profile/source revisions, unsupported cases, limitations and follow-up IDs. Attach stage/image/report evidence required above. For measured changes provide raw before/after samples and environment; otherwise state no performance claim. Record any acceptance gate still open; do not mark the task complete when required evidence is missing.
