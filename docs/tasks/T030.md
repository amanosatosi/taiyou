# T030 — Release verification and platform hardening

Status: planned. Suggested owner: **Sol 6.1 integration; Astra release review**. Scope: one focused implementation session unless explicitly bounded as research; split with coordinator approval if unexpected work appears.

## Objective

Demonstrate the initial usable renderer gate with complete compatibility, safety and platform evidence.

## Prerequisites

[T028](T028.md), [T005](T005.md), [T029](T029.md). These must meet their acceptance gates before dependent work starts.

## Files and modules

Create planned release workflows and docs/RELEASE.md; harden only failures assigned explicit regression issues. All creation paths in this section are planned; inspect for intervening implementations before editing.

## Technical contract

G2 and V1–V9: all declared supported cases pass, full inventory visible, real protected gates active, no hidden safety failures, licensing/notices complete before packaging. Pin compiler/native/action versions and document host integration limits.

## Expected behavior

Documentation-only PR uses cheap checks; native change triggers platform lanes; candidate cannot weaken baseline gates; release artifact identifies ABI/profile/native versions and unsupported features.

## Implementation guidance

Do not turn release hardening into a feature sprint. Missing original VSFilter captures or color-space behavior are explicit scope limitations; release claim must match approved profile.

Read [GOALS](../GOALS.md#g2-initial-usable-renderer). Read [DEVELOPMENT](../DEVELOPMENT.md#d3-github-actions-design).

## Acceptance criteria

Windows/Linux/macOS smoke+supported comparison+FFI pass, fuzz/sanitizer evidence published, controlled perf baseline archived, maintainer signs scope/license and compatibility report.

## Verification

Run locked workspace checks, supported full suite, complete external report, determinism matrix, C smoke, safety lanes and benchmark baseline. Archive checksums and all limitations. Commands referring to Cargo/xtask are established by the task that creates that tooling; do not report them run before it exists.

## Forbidden changes

No baseline regeneration, support shrinkage without protected review, unknown license redistribution or universal pixel-perfect claims. Ordinary implementation cannot modify protected expected assets, tolerances or support classifications.

## Completion report

Report T030, integration base and commit IDs (or explicitly no Git), changed files, exact commands and pass/fail results, fixture/profile/source revisions, unsupported cases, limitations and follow-up IDs. Attach stage/image/report evidence required above. For measured changes provide raw before/after samples and environment; otherwise state no performance claim. Record any acceptance gate still open; do not mark the task complete when required evidence is missing.
